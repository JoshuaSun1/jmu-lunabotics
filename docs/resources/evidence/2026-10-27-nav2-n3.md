# Nav2 Stage N3 development-TF evidence — 2026-10-27

## Scope and acceptance boundary

This record covers the specification-permitted temporary TF-provider route for
the AprilTag-only mock profile. It does not claim production continuous
localization. The profile starts no map server, costmap, planner, controller,
behavior tree, final `/cmd_vel` publisher, hardware interface, or motor output.

The selected test split is:

```text
map -> odom       identity, dynamic, fused-pose measurement timestamp
odom -> base_link fused pose, dynamic, same measurement timestamp
```

`apriltag_development_tf_bridge` consumes
`/localization/fused_pose` (`geometry_msgs/msg/PoseWithCovarianceStamped`) and
`/localization/valid` (`std_msgs/msg/Bool`). It publishes the two transforms in
one `/tf` (`tf2_msgs/msg/TFMessage`) sample and reports on `/diagnostics`. It
publishes exactly once per new validity-approved pose, performs no propagation
or timestamp refresh, stops producing samples on invalidity/staleness, and is
replaced—not run alongside—by the future local/global EKFs.

## Safety/configuration evidence

- The configuration defaults `allow_test_only_tf: false` and labels physical
  robot use `prohibited`.
- The N3 launch separately defaults `enable_development_tf:=false` and
  `allow_test_only_tf:=false`; both must be true to start the broadcaster.
- The launch and node reject `production_ekfs_enabled:=true` with development
  TF, and require `localization_profile:=apriltag_development_only`.
- The launch contains one bridge/broadcaster and no EKF, Nav2 server, drive
  controller, `lb_hardware` node, or final command remap.
- Invalid, wrong-frame, zero/future/stale/out-of-order, nonfinite,
  invalid-quaternion, and invalid-covariance input fails closed. The existing
  Batch 1 `0.50 s` validity/command gate remains the motion lock.
- A TF buffer may retain the last old transform after loss. Original source
  timestamps make that staleness observable; retained data is not current TF.

The launch started exactly these three intended processes:

publisher introspection passed in the focused runtime test.

## Remaining limitations and replacement gate

- There is no `/odom/wheel`, validated ZED/mock IMU, local EKF, global EKF,
  velocity estimate, or localization propagation through tag loss.
- The `0.50 s` freshness limit is team-approved development policy, not an
  experimentally tuned detector/stopping bound.
- `map=odom` makes the global fused pose temporarily appear on the local edge;
  it is a mock-navigation convenience, not production frame semantics.
- CPU, memory, DDS latency, detector latency/rate, transform jitter, braking,
  stopping distance, and long-duration behavior were not measured.
- Target Humble/Jetson and physical-system tests remain required. Before
  physical use, remove this provider and validate the local EKF as sole
  `odom -> base_link` owner and global EKF as sole `map -> odom` owner.
