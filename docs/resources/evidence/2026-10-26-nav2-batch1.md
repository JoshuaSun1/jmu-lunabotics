# Nav2 Batch 1 development evidence — 2026-10-26

## Scope

This record covers Nav2 Stages N0-N2 only: dependency/readiness auditing, the
AprilTag-only fused-pose boundary, localization-aware navigation command gate,
and the estimated development footprint/limits profile. It does not establish
continuous localization, Nav2 server operation, costmaps, TF readiness,
physical motion safety, or competition readiness.

Base revision at the start of implementation: `c38df79` (`Removed docker and
added a nav2 specification sheet...`). Final verification was completed on
2026-10-27. The implementation commit is to be recorded after review.

## Implemented boundary

- `fused_pose_passthrough` subscribes to
  `/localization/apriltag_pose`
  (`geometry_msgs/msg/PoseWithCovarianceStamped`) and publishes each accepted
  sample unchanged on `/localization/fused_pose`.
- It publishes transient-local, reliable `/localization/valid`
  (`std_msgs/msg/Bool`) and `/localization/status`
  (`diagnostic_msgs/msg/DiagnosticArray`).
- Accepted input must be in `map`, have a nonzero, current, ordered timestamp,
  finite pose/covariance values, a nonzero quaternion, and nonnegative
  covariance diagonal. The development freshness timeout is `0.50 s`, checked
  every `0.05 s`.
- `navigation_command_gate` independently checks fused pose and validity. It
  consumes future `geometry_msgs/msg/TwistStamped` controller output on
  `/cmd_vel_nav_raw` and publishes on `/cmd_vel_nav` only while localization
  is current. It publishes explicit zero while blocked and on the transition
  from permitted to blocked.
- Neither node publishes TF. `nav2_batch1.launch.py` starts no Nav2 server,
  map server, controller manager, `/cmd_vel` publisher, hardware, or motor
  output.
- `robot_limits_development.yaml` records the team-estimated centered
  `1.10 x 0.60 m` polygon, zero provisional padding, and existing mock motion
  limits. Physical use is explicitly prohibited.

Result: all four packages completed; `25 tests, 0 errors, 0 failures,
0 skipped`.

The first full-suite attempt exposed a validity-loss race: if upstream
published `valid=false` after the pose crossed its timeout but before the
gate's own timer callback, recomputing the prior permission state suppressed
the transition zero. The callback now compares against the gate's last
published state. The integration test cancels the gate timer after a permitted
command so the upstream-validity-loss path deterministically proves that it
publishes zero. The focused contracts remained `30 passed`.

Repository hygiene hooks for every changed Batch 1 file passed with Black
excluded from the combined hook invocation. Black 24.10.0 was then run in
`--check --line-length=100` mode once per changed Python file; all eight files
were unchanged. The per-file invocation is necessary in this sandbox because
Black's multi-file multiprocessing manager cannot create its local socket.
`git diff --check` also passed.

## Safety, resources, and limitations

- The gate is defense in depth, not an E-stop, motor watchdog, final mux, or
  safety supervisor.
- No active Nav2 goal exists in Batch 1, so action cancellation and the rule
  against automatic goal resumption remain Stage N5-N6 acceptance items.
- Raw command timestamp/frame age validation and final mux publisher-loss
  behavior remain Stage N5 decisions; Batch 1 rejects nonfinite commands.
- No CPU, memory, latency distribution, detector rate, braking distance, or
  endurance result was measured. The `0.50 s` timeout, `0.05 s` check periods,
  footprint, padding, and motion limits remain development assumptions.
- The current host result is ROS 2 Jazzy/x86 only and does not validate ROS 2
  Humble, Jetson/arm64, ZED, DDS networking, or physical hardware.
